# 2026-10-28 P3 E4: live-lock and action gate

Status: built, then fixed after the 2026-10-28 security review (see "Review fixes"). After the fixes: lint 0 findings, `npm test` 467/467, `npm run ci` 12/12. Invariant matrix: 6156 cases, all hold.

## What was built

`services/event-core/livelock/`: `catalogue.mjs` (load, validate, deny categories), `provenance.mjs` (snapshot, validation, taint), `gate.mjs` (`createActionGate`: request, confirm, panic, setLiveState, forSource), `index.mjs`. Data: `data/actions/catalogue.json` + `catalogue.schema.json` (27 actions). Wired as `core.actions` in `services/event-core/index.mjs` (`opts.actions: false` turns it off; `opts.actions = { catalogue?, executor?, onDecision?, now?, wall?, ttlMs?, maxPending?, liveStaleMs? }`). The gate emits `system.panic` and `system.livestate` on the bus through `core.ingest`.

`request()` is synchronous. It takes one plain-data snapshot, does map lookups, one JSON canonicalisation, and (confirm issue only) one SHA-256 and one `randomBytes`. No I/O, no await. The catalogue file is read once at start-up. A legacy check: the "yes" / "yes, on air" wording comes from `legacy/CLAUDE.legacy.md` line 12 (a convention in the instructions plus the `--live-ok` flag in `legacy/tools/cam-pop.mjs`; there is no confirmation code in legacy to port).

## Rule table as implemented (after review fixes)

Entry: one plain-data snapshot of the request (own data properties only: id, source, actor, params, provenance). Decisions and dispatch use only the snapshot. Any throw inside `request`, `confirm`, `panic` or `setLiveState` refuses with `internal-error` (audited; never allow on error). Evaluation order, first match wins. `tainted` = source is `chat`, or the copied provenance chain is not clean (see Taint).

| # | Condition | Verdict, reason |
|---|---|---|
| 0 | request is not a plain object (Proxy, array, class instance, odd prototype), or has an accessor on id, source, actor, params or provenance | refuse `bad-shape` |
| 1 | `source` not one of ui, api, chat, rule, remote, system (or the handle's fixed source, see `forSource`) | refuse `bad-source` |
| 2 | action id not in catalogue | refuse `unknown-action` |
| 3 | params not plain JSON (functions, NaN, Date, Proxy, getters, depth > 12, own `__proto__`/`constructor`/`prototype` key anywhere, canonical size > 8192 bytes) | refuse `bad-params` |
| 4 | panic on, and (tainted or source = rule) | refuse `panic` |
| 5 | tainted, id in a deny category (any class, read included) | refuse `chat-forbidden` |
| 6 | tainted, `chatAllowed` not true (any class, read included) | refuse `chat-not-allowed` |
| 7 | tainted, `chatAllowed` true and not in a deny category | allow `chat-allowed`, no confirmation ever offered |
| 8 | `panic.set`, source not in ui/api/system | refuse `source-not-permitted` |
| 9 | `panic.set` | allow `panic-engaged` (panic engaged, pending cleared, event emitted) |
| 10 | `panic.clear`, source not in ui/api | refuse `source-not-permitted` |
| 11 | `panic.clear`, panic off | refuse `not-in-panic` |
| 12 | `panic.clear` | confirm; phrase by the live rule: `yes` offline, `yes, on air` live or unknown |
| 13 | class `read` (untainted) | allow `read` |
| 14 | the requesting source already has `maxPending` (16) pending confirmations | refuse `too-many-pending` (nothing is evicted) |
| 15 | write or on-air-write, untainted (ui, api, remote, system, clean rule) | confirm; phrase `yes` if the effective live state is `offline`, else `yes, on air` |

Confirmation (`confirm(confirmId, phrase, actionHash, {source})`), checked in this order:

| Check | Refusal reason | Spends the confirmation? |
|---|---|---|
| confirming source not ui or api | `source-not-permitted` | no |
| id never issued, cleared by panic, or older than the last 256 used ids | `unknown-confirm` | n/a |
| id already used (within the last 256 used ids) | `replayed` | n/a |
| now >= expiresAt (TTL 60 s) | `expired` | yes |
| `liveEpoch` differs from issue time, or the effective live state differs | `live-state-changed` | yes |
| actionHash differs | `hash-mismatch` | yes |
| phrase differs after trim + lower-case | `wrong-phrase` | yes |
| internal error (broken clock, hook, random source) | `internal-error` | yes |
| otherwise | allow `confirmed` (or `panic-cleared`), then dispatch | yes |

Live state: `setLiveState('offline'|'live'|'unknown', {source, provenance})` is allowed only from `system` or `api` with untainted provenance; anything else is refused `source-not-permitted`. Every change bumps `liveEpoch`. The state starts `unknown`, which counts as live.

Staleness: if no accepted update has arrived within `liveStaleMs`, the effective state is `unknown`. Proposed default: 15 000 ms, configurable (finite positive integer). Reason: the studio feed (P6) should re-assert the state at least every 5 s, so 15 s is three missed updates. An unchanged update refreshes the timer without bumping the epoch. Until P6 the state is mocked, so a caller that does not refresh it gets "yes, on air" after 15 s.

On `system.disconnected` of the studio feed, the caller must call `setLiveState('unknown', {source: 'system'})`. The gate does not subscribe to the bus itself. `unknown` emits no `system.livestate` event, because the E1 schema carries a boolean only.

Other rules: `panic()` is allowed from ui, api and system only, and refused if its provenance is tainted. All pending confirmations are cleared on panic (cleared first, then audited). Memory only: a restart (new gate) knows none. `ttlMs`, `maxPending` and `liveStaleMs` must be finite positive integers. Anything else (NaN, Infinity, 0, negative, fractional, string, null) throws `TypeError` at construction.

Transport binding: `gate.forSource(source)` returns a frozen handle `{source, request, confirm, panic, setLiveState}` whose source is fixed. A `source` in the request object or ctx is ignored. The E6 API layer must create one handle per authenticated transport and never take `source` from a request body. Bare `gate.request()` reads `action.source` and is for in-process callers only.

### Taint (provenance.mjs)

Provenance node: `{kind, eventId?, parent?}`. The gate first copies the chain (`copyProvenance`): own data properties only, no getter is run, Proxies and non-plain objects are refused, and the walk stops at depth 16 (cycles included). Anything unreadable becomes a node `{kind: 'invalid'}`.

Validation against E1: each `kind` must be an E1 event kind (`KINDS` in `model.mjs`) or `rule`, `schedule`, `hotkey`. Each `eventId` must match the E1 id regex `^e[0-9a-f]{12}-[0-9a-f]{8}-[0-9a-f]{8}$`. The actor must be an E1 pseudonymous id (`^[0-9a-f]{32}$`), or, on an untainted request only, a local label `^[a-z][a-z0-9-]{0,31}$`. Anything else becomes `invalid`. So no free text reaches the audit through provenance or actor.

A `rule` node takes the taint of its `parent` (missing parent means tainted). Clean roots: E1 `system.*` kinds, `schedule`, `hotkey`. Unknown `system.*` kinds are now `invalid`, which is tainted. Everything else is tainted: `chat.*`, `alert.*`, `invalid`, malformed nodes, chains deeper than 16. A `rule` source with no provenance is tainted. A non-rule source that carries chat provenance is tainted too.

### Deny categories (fixed in code, `catalogue.mjs` `isChatDenied`)

Tainted requests use an allowlist: they may reach only ids that are `chatAllowed: true` AND not in a deny category. An id is in a deny category if any rule matches:

1. It is in `DENY_SET`: `stream.start`, `stream.stop`, `record.start`, `record.stop`, `output.change`, `scene.delete`, `layer.delete`, `preset.delete`, `settings.change`, `device.change`, `mic.main.mute`, `panic.set`, `panic.clear`.
2. Its first segment is one of `stream`, `streams`, `record`, `records`, `recording`, `recordings`, `output`, `outputs`, `rung`, `rungs`, `sink`, `sinks`, `encoder`, `encoders`, `delivery`, `settings`, `setting`, `config`, `device`, `devices`, `panic`, `gate`, `livestate`, `live`.
3. Its target is one of `stream`, `record`, `output`, `settings`, `device`, `gate`.
4. Main mic: a segment `mainmic`; or a segment `main` plus one of `mic`, `mics`, `microphone`, `microphones`; or target `audio` with a segment `main`.
5. A destructive verb as any segment: `delete`, `del`, `remove`, `rm`, `destroy`, `erase`, `purge`, `wipe`, `clear`, `reset`, `truncate`, `trash`, `discard`, `uninstall`, `overwrite`, `unlink`, `drop`. The one exception is `marker.drop`, which places a timeline marker.

This is enforced twice:

- At catalogue load: `chatAllowed: true` on any deny-category id fails with `CatalogueError`. A `DENY_SET` id also cannot be class `read`.
- In the gate, on every tainted request, before any class check.

The gate never uses a caller's Map. Any catalogue (parsed JSON or Map) is rebuilt through `buildCatalogue` and copied into a private Map of frozen entries. It is exposed only as a frozen read-only view (`get`, `has`, `ids`, `size`). `createEventCore` no longer has a `catalogueMap` seam: passing one throws `TypeError`.

### Catalogue (27 ids)

Owner default (2026-10-28): every entry is `chatAllowed: false`. The owner turns specific ones on in later phases. So with the committed data, every tainted request is refused.

- read: `state.read`, `scene.list`, `health.read`. Of these, only `scene.list` looks harmless to chat (scene names, already visible on stream). `state.read` and `health.read` expose live state and output stats and should stay off. All three are off now.
- Not in a deny category (the owner could chat-allow these later): `scene.switch`, `scene.create`, `layer.show`, `layer.hide`, `layer.create`, `effect.fire`, `preset.apply`, `camera.toggle`, `replay.save`, `marker.drop`, `chat.reply`, and the three reads.
- Deny set: the 13 ids above.
- Classes: on-air-write for `scene.switch`, `layer.show/hide`, `effect.fire`, `camera.toggle`, `stream.start/stop`, `output.change`, `mic.main.mute`; write for the rest. `write` and `on-air-write` behave the same for now; the owner is deciding whether on-air writes while live need a two-step confirmation.

## Design choices beyond the spec

1. `chatAllowed: true` is the catalogue's standing authorisation, so a chat-tainted request for a chat-allowed action (not in a deny category) is allowed with no confirmation, whatever its class. Committed default: none are chat-allowed. C2's per-scene `chatControllable` flag, cooldowns and role checks sit on top later and are not in the gate.
2. `write` and `on-air-write` behave identically in P3 (same phrases, same chat rule). The class is kept in the data and passed to the executor. Owner decision pending.
3. `panic.set` and `panic.clear` are catalogue ids and in the deny set (chat can neither engage nor clear panic). `panic.set` from ui/api/system takes effect at once through `request` as well as `panic()`.
4. `remote` may not confirm and may not trigger panic in P3 (stricter than "like api"). A remote request still gets a confirm token that a ui or api caller must complete. P15 decides both.
5. `system` may request (gets a confirm like api), panic, and set live state, but may not confirm.
6. An untainted `rule` (schedule, hotkey, system-event root) is treated like api: its writes need a ui/api confirmation. Automation that must run unattended is not covered yet.
7. Provenance is fail-safe: unknown kinds, malformed nodes, accessors, Proxies, missing parent on a `rule` node, and depth over 16 are tainted.
8. A non-rule source carrying chat provenance is tainted (e.g. a ui button wired to a chat suggestion must not forward the provenance).
9. A confirmation is spent by any failed check except wrong confirming source. A typo means re-request. Not spending on wrong source stops a chat-reachable path from cancelling pending confirmations. A bounded set (256) of used ids lets the replay reason be `replayed`; beyond that an old id reports `unknown-confirm`, which is still a refusal.
10. Params are snapshotted (canonical JSON round trip) at request time; later mutation by the caller does not change what runs.
11. A live state change keeps pending confirmations, but they fail with `live-state-changed`; `panic` is the only thing that clears them.
12. Expiry uses a monotonic clock (`performance.now`) by default so a wall-clock change cannot extend a TTL. Audit stamps use wall time. Both are injectable; a non-finite or throwing clock refuses `internal-error`.
13. `request()` returns the dispatch result in `dispatch`: a plain `{ok, result|error}` for a sync executor, or a promise that never rejects for an async one. The verdict stays `allow` if the executor fails.
14. The executor receives a frozen `{id, params, source, actor, class, target, tainted}`.
15. Audit record types: `request`, `confirm-issued`, `confirm-accepted`, `confirm-refused` (also expiry prune and pending cleared by panic), `panic`, `panic-clear`, `live-state`. Fields: type, actionId, source, actor (validated, see Taint), provenance summary `{tainted, kinds[], eventIds[]}` (validated), verdict, reason, liveState, panic, ts (ISO), mono, plus actionHash / confirmingSource / to where relevant. `params` and confirmId are never included. The audit record is built before any state change or dispatch; if it cannot be built (broken clock), the call refuses. A throwing hook is ignored.
16. Panic and live state are memory only: a restart starts with panic off and live state `unknown`.
17. `system.livestate` is emitted only when the state changes to `offline` or `live`. `system.panic` is emitted on engage (reason from the caller, else `panic`) and on clear (`cleared`).
18. The catalogue schema does not require `chatAllowed` (default false); the loader and schema agree.
19. The ajv schema check lives in the test only; runtime validation is hand-written (stdlib only).
20. Pending quotas are per requesting source, so the worst case is 5 x 16 pending (chat never gets one).
