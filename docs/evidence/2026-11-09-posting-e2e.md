# Auto posting end to end against a local fake YouTube, 2026-11-09

Test: `tests/posting-e2e.test.mjs` (6 tests). A real HTTP server on 127.0.0.1 plays Google (resumable insert sessions, chunk
PUTs with Content-Range, progress queries, videos.list). Seams used: `fetchImpl` (rewrites the googleapis host to the local
server, so nothing can leave the machine) and a fake token provider (`auth`). No OAuth, no secrets, no real network.

Chain exercised: uploads.json rows (montage short, long horizontal montage, won reel) -> `packageUploads` -> auto rules
(`kinds`) -> resumable upload (16-byte chunks) -> `checkPostStatus` -> `markPosted`. Targets: youtube-shorts and youtube-video.

## Cases
1. Success: 3 videos uploaded private to the right targets, queue `done`, uploads.json `posted` filled, status check
   (found / uploaded / private / succeeded), no token in the queue file, a second pass posts nothing.
2. Failed upload retried with backoff: init fails twice (503); waits 5 min, then 10 min (doubling); no early retry; one video.
3. Rejected chunk (403) then retry: same session continued from Google's byte count, one init, one video.
4. Answer lost but upload completed (server stores the video, drops the connection on the final chunk).
5. Same, and the progress query also fails transiently on the retry.
6. Live: zero requests while a stream sink is live or the state is unreadable (nothing even approved); a stream that starts
   after the first chunk stops the upload, session kept, resumed after the stream ends; one video.

## Bugs found (cases 4 and 5 failed before the fix)
- Answer lost: the resume query on a finished session got HTTP 200, `queryProgress` returned the total byte count, the chunk
  loop was skipped and the code threw `upload-failed` ("loop ended without a finished response"). The video was on YouTube
  but never recorded (no ledger entry, no `posted`), and the queue retried it 8 times, then marked it failed.
- Possible duplicate: in `uploadVideo`, ANY failure of the stored-session progress query (a 503, a network blip) discarded the
  session and started a new one. If the first upload had completed, that uploads the video a second time.

## Fix (narrow, `services/posting/youtube.mjs`)
- `queryProgress` returns `{ resource }` when Google answers a query on a finished session with 200/201; `uploadChunks` and
  `uploadVideo` use that resource as the finished upload (ledger + `posted` get written, no retry).
- A new session is started only for 404/410 (`upload-session-gone`); any other query failure is rethrown, the queue keeps
  the session and retries later.

## UNVERIFIED / residual
- UNVERIFIED against real YouTube: that a progress query on a completed resumable session returns 200/201 with the video
  resource (Google's resumable-upload documentation says so; the fake models it). If real Google answers differently
  (e.g. 404 after completion), the old "new session" path would upload a duplicate. No idempotency marker lookup was added:
  YouTube has no custom metadata field, and searching needs `videos.list`/`search` scope and quota (itself UNVERIFIED for the
  upload-only scope). Mitigation if it shows up: on `upload-session-gone`, list the channel's recent uploads (private
  included) and match title + size before re-uploading.
- The fake server is our model of Google, not Google.
- Pre-existing and unrelated: `tests/posting-youtube-cli.test.mjs` "unknown subcommand is a usage error" fails on the base
  branch too (checked with the change stashed).
