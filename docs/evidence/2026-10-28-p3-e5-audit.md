## What was built

`services/event-core/audit/`:

Wiring: `createEventCore({ audit: { dataDir, ...} })` creates `core.audit` (null without the option; behaviour unchanged). Moderation `onVerdict` (drops and flags), the gate's `onDecision`, and every published `system.*` event (connected, disconnected, panic, livestate) go to the audit; published chat and alert text goes to `chat_raw`. The caller closes `core.audit`.

## 1. Database

- File: `<dataDir>/event-core.db`. Opened with `journal_mode=WAL`, `synchronous=FULL`, `secure_delete=ON`, `auto_vacuum=INCREMENTAL` (set before the first table exists; read back as 2 in the tests).
- **`synchronous=FULL`, justified.** In WAL mode, NORMAL can lose the last committed transactions after an operating-system crash or power cut (never corrupts). FULL syncs the WAL on every commit, so an acknowledged batch survives power loss too. The cost is invisible: the commit runs on the writer thread, and measured it is cheap here (table below): FULL 1.05 ms per 200-row commit at about 170k to 189k rows/s, NORMAL 0.65 ms at about 260k rows/s. The audit is a record of what the system did; the live path never waits for it, so the extra 0.4 ms per batch costs nothing the stream can see. UNVERIFIED: real power-loss behaviour (only process kill was tested; see Crash test).
- **Schema version table:** `schema_version(version PK, name, applied_at)`. Migrations are forward only, each in its own transaction (a failing one rolls back; tested). Tests: empty database to v1, reopen applies nothing, an injected v2 applies once, old code refuses a v2 database, a broken migration leaves v1.
- **Single writer, and which lock.** One process owns the database. `createAudit` takes an exclusive SQLite lock (`PRAGMA locking_mode=EXCLUSIVE` + `BEGIN EXCLUSIVE`, never committed) on a separate file `<dataDir>/event-core.db.lock` and throws `AuditError('DB_LOCKED')` if anyone else holds it. Chosen over a pid lock file because the operating system drops the lock when the owner dies by any means (kill, crash, power loss): no stale lock to clean up, no pid reuse to guess about. It is a separate file so readers (`audit verify / backup / export`) still read the WAL database while the owner runs. Tested in the same process, in a second process, and after the owner's death (the crash test re-takes the lock after every kill). The `purge` CLI needs the lock, so it refuses while the core runs (a running core purges itself at start-up and daily; an API-triggered purge arrives with E6).

## 2. Tables

- `audit` (append-only, hash-chained): `id, ts, type, subtype, event_id, pseudo_id, action_id, rule_id, source, verdict, reason, detail, prev_hash, hash`. `BEFORE UPDATE` and `BEFORE DELETE` triggers `RAISE(ABORT)`. Types: `decision` (gate `onDecision`: request, confirm-issued, confirm-accepted, confirm-refused, panic, panic-clear, live-state), `moderation` (drops and flags: verdict, reasons, blocklist pattern indexes as `rule_id`), `system` (connected, disconnected, panic, livestate events; `purge`, `audit-overflow`). No raw text or display name: only event ids, pseudo ids, action ids, rule ids, verdicts, reasons, timestamps, and a `detail` JSON of numbers, booleans and single-word tokens.
- `audit_head(k=1, last_id, row_count, head_hash)`: updated in the same transaction as every append; truncation check.
- `chat_raw(event_id PK, received_at INTEGER ms, platform, display_name, text)`: outside the chain. Only `chat.message` text and alert `message` text go here (also for moderation-dropped and flagged events, so the user can review a drop within the window).

## 3. Writer off the hot path

Recorders (`observe`, `recordVerdict`, `recordDecision`, `recordSystem`) validate a few fields, push a plain object on an in-memory array and return. No hashing, no disk, no await. A batch is handed to the writer when 200 rows are queued (`setImmediate`) or 100 ms after the first queued item (`setTimeout`). The writer hashes and commits one transaction per batch.

Two options were built and measured (`node tools/bench/audit-writer-compare.mjs`, 20 000 synthetic events per run, 3 runs after a warm-up, medians; ingest in bursts of 50 with a `setImmediate` yield between):

| writer | main-thread block per batch p50 / p95 / max | ingest p50 / p95 / p99 | event-loop delay p99 / max | rows written |
|---|---|---|---|---|
| no audit (baseline) | n/a | 0.006 / 0.011 / 0.013 ms | 1.46 / 1.82 ms | n/a |
| inline (`setImmediate` flush on the main thread) | 1.031 / 1.306 / 4.673 ms | 0.007 / 0.013 / 0.021 ms | 2.52 / 5.60 ms | 14 286 (58 batches) |
| worker (`worker_threads`) | 0.079 / 0.106 / 0.131 ms | 0.007 / 0.013 / 0.018 ms | 1.62 / 2.53 ms | 14 286 (58 batches) |

**Choice: the worker thread.** Per-batch main-thread blocking is about 10x lower at p95 (0.11 ms against 1.3 ms) and 35x lower at the maximum (0.13 against 4.7 ms; the inline max is a transaction with an fsync), and the event-loop delay maximum halves. The bus ingest p95 with the audit attached is 0.013 ms in both modes against 0.011 ms with none, so the audit adds about 0.002 ms to the p95 ingest call; PB-12 is 20 ms. The inline writer costs a transaction on the main thread every batch, which under load would land in the middle of event handling. The worker costs a structured clone of the batch (0.08 to 0.13 ms), complexity (a second thread, message protocol), and it makes purge / verify asynchronous.

Bench harness entry: `tools/bench/benches/event-core-audit.mjs` (id `event-core-audit`, budget PB-12, metrics `ingest_p95_ms`, `block_p95_ms`, `rows_per_s`). A run on this machine: ingest_p95 0.01 ms, block_p95 0.11 ms, rows_per_s 178 612 (FULL, 200-row batches, store used directly). It is a new bench id, so it sets its own first baseline; no existing baseline was changed or accepted. PB-12 itself stays UNVERIFIED until E7 measures ingest to dispatch end to end.

- **Batch values:** 200 rows or 100 ms, whichever first. Both configurable (`batchMax`, `batchMs`).
- **Queue cap:** 10 000 audit rows and 20 000 raw rows, each counting queued plus in flight (configurable). When full, the newest item is dropped and counted (never blocks, never throws). The next batch carries a `system / audit-overflow` row with `{droppedAudit, droppedRaw}`. Tested in inline mode (exact counts: 12 pushed into a cap of 5 gives 7 dropped, row detail `{"droppedAudit":7,"droppedRaw":7}`) and with the worker under a 20 000-row flood.
- **Each batch is one transaction** (raw rows and audit rows together; the head row is updated inside it).
- **Maximum audit loss on a crash:** one batch interval, 100 ms of queued items (up to 200 rows per batch waiting), plus a batch that was in flight but not yet committed. Committed batches survive a process kill (FULL). Rows are lost whole batches at a time, never partially. If the writer thread dies, the failure is counted (`writeErrors`, `lost*`), the queue stops growing, and the core keeps running; it is not restarted automatically (the supervisor, P4/P5, would do that).

## 4. Retention

- `purge({now, olderThanDays=30, all=false, mode})` deletes `chat_raw` rows with `received_at < now - days*86400000` (strict, so exactly 30 days is kept). It writes one audit row (`system/purge`, detail `{purged, mode, olderThanDays}`: a count, never content) in the same transaction as the delete.
- Runs at start-up (after the writer is ready, off the main thread) and every 24 h (default scheduler timer is `unref`'d, tested; an injected scheduler is used in tests).
- Manual: `node services/event-core/cli.mjs audit purge [--older-than-days N]`. `--all` deletes all raw chat and needs the typed word `yes` (interactive prompt, or `--confirm yes` for scripts); any other answer, or no terminal, deletes nothing. `--all` with `--older-than-days` is refused.
- **Scrubbing, and why this choice.** `secure_delete=ON` zeroes deleted content in the page being rewritten. After the delete: automatic purges run `PRAGMA incremental_vacuum` (returns the freed pages to the OS, so the file shrinks, without rewriting the whole database) and `wal_checkpoint(TRUNCATE)` (copies the zeroed pages over the old ones in the main file and empties the WAL). `--all` runs a full `VACUUM` first (rare, destructive anyway, rewrites everything). Incremental vacuum was chosen over a daily full `VACUUM` because the audit grows for ever and a full rewrite would hold the writer for the whole database each day; the test below shows the weaker daily method is enough.
- **Secure-delete proof** (`tests/event-core-audit.test.mjs`, and the manual run below). 1 500 synthetic chat rows containing a marker, some padded to 5 000 bytes so they use overflow pages:

```
after insert (before checkpoint)
  event-core.db: 4096 bytes, 0 marker hits
  event-core.db-wal: 1371992 bytes, 1500 marker hits
after checkpoint, before purge
  event-core.db: 1343488 bytes, 1500 marker hits
  event-core.db-wal: 0 bytes, 0 marker hits
purge { purged: 1500, cutoff: 1790553600000, all: false }
after purge (delete + incremental_vacuum + checkpoint TRUNCATE)
  event-core.db: 32768 bytes, 0 marker hits
  event-core.db-shm: 32768 bytes, 0 marker hits
  event-core.db-wal: 0 bytes, 0 marker hits
```

  The test also plants a second copy that is only in the WAL (marker found in the `-wal` file before the purge) and checks no byte of `.db`, `-wal` or `-shm` holds it afterwards. A control test shows the check can fail: with `secure_delete=OFF` and no vacuum, the same DELETE plus checkpoint leaves the marker in the file. `--all` (VACUUM) is tested the same way.

## 5. Chain verification

`node services/event-core/cli.mjs audit verify` opens the database read-only and, in one read snapshot, runs `PRAGMA integrity_check`, checks every row (`id` continuity, `prev_hash`, recomputed `hash`), and compares the head record (row count, last id, head hash). Exit 0 / 1; on failure it prints the first bad row id and a reason: `hash-mismatch`, `prev-mismatch`, `id-gap`, `truncated` (head ahead of the table; id = first missing), `head-mismatch`, `head-missing`, `integrity-check`. Works while the core runs. Tested (copies with the triggers dropped): edited row (found at its id), edited row plus its own hash (found at the next row), deleted middle row, truncated tail (`truncated`, id 16 of 20), head rewound, head deleted; plus the CLI exit codes through a real process.

## 6. Backups, exports, logs

- `audit backup <dest>`: creates a fresh database at `<dest>.partial`, attaches the source, copies `audit`, `audit_head` and the version row in one read snapshot (raw chat is never read into the copy, so it also never sits in the copy's free pages; this was chosen over `VACUUM INTO` plus a drop, which would put the raw text on disk in the copy first). It then verifies the copy (chain, head, integrity, zero `chat_raw` rows), switches it to a single file (`journal_mode=DELETE`), and renames it into place. Refuses a destination inside the repo (real-path comparison) or one that already exists.
- `audit export --format jsonl [--out FILE]`: the `audit` table only, one JSON object per line, stdout or a new file; same repo and exists refusals.
- Marker test (`tests/event-core-audit-privacy.test.mjs`): a unique marker and a unique display name are planted in chat, an alert message and a moderation-dropped message. The test shows the marker in the live database files and 22 raw rows, then greps every byte of the backup directory, the export output (stdout and file) and the CLI processes' stdout/stderr: zero hits for the marker and the name. The audit tables themselves (all columns) hold neither. Backup and export also run through the real CLI while the core holds the lock.
- Logs: the audit module prints nothing by default except `[audit] <level>: <code>` on a failure (codes only; tested with a database from a newer schema and a regex over every line). The test captures `console.*` through a complete workflow (ingest, flush, verify, purge, a refused second owner, CLI verify / purge / export) and finds no marker or name. Worker errors cross the thread boundary as codes, never SQLite messages.

## 7. Pseudonymity

Pseudo ids are the E1 ids (`derivePseudoId`, HMAC-SHA256 of platform and platform user id with the key in `pseudo.key`). Decision rows get the pseudo id from the request actor (E4 only lets a pseudo id through for tainted requests), otherwise from a 4 096-entry event-id to pseudo-id cache filled as events pass through. Rows with no resolvable user have none.

**UNVERIFIED, proposed, not built: erasing one viewer.** If a viewer asks to be forgotten: (a) delete their `chat_raw` rows (needs a pseudo-id index on `chat_raw`; today the raw table is indexed by time only, so a selective delete is a scan); (b) the audit rows cannot be edited or deleted (append-only, chained), so the pseudo id would be replaced by rotating the key and keeping a mapping, or by appending a "pseudo id X retired" row and having tooling treat it as erased. Rotating `pseudo.key` would unlink old and new ids for everyone. Needs the owner's decision and a legal read; not designed further here.

**Note added 2026-10-29 (E4b independent review, finding 11): a dry-run row can be joined to raw chat until the purge, by design.** A chat dry-run decision row (`type=decision`, `verdict=dry-run`, see `docs/evidence/2026-10-28-p3-e4b-dryrun-two-step.md`) stores the internal id of the triggering chat event in `event_id`. That is also the `chat_raw.event_id` key. So, inside the 30-day raw-chat window, someone who can read both tables can join a dry-run row to the viewer's text and display name. The audit row itself holds no text, display name or platform user id (review attack A10). This is by design, so the owner can review what chat would have triggered; once the raw row is purged (30 days, or `purge --all`), the join is gone and the audit row keeps only the action, rule, pseudo id, verdict and time.

## Design choices beyond the spec

1. **Lock = exclusive SQLite lock on a separate `.lock` file** (not a pid file), see section 1.
2. **`synchronous=FULL`**, section 1.
3. **Both writers kept.** `mode: 'inline'` exists for tests and as the measured alternative; `worker` is the default.
4. **`auto_vacuum=INCREMENTAL` + `incremental_vacuum` for daily purges, full `VACUUM` only for `--all`.**
5. **`sanitise.mjs`**: every audit field must match a strict pattern (event ids, 32-hex pseudo ids, single-word tokens up to 64 characters from `A-Za-z0-9_.:,-`, no spaces); anything else is stored as `(redacted)`. A sentence can never be stored; a single word can (so this is defence in depth behind the recorders, which already read only fixed fields, not the guarantee).
6. **Dropped and flagged chat keeps its raw text in `chat_raw`** (same 30 days) so the owner can review a moderation decision. `observe` skips events that already went through `recordVerdict`.
7. **Backup built by copying audit tables into a fresh database**, not `VACUUM INTO` plus a drop, so raw chat never touches the backup file. The backup is verified before the rename.
8. **`purge` CLI refuses while the core owns the database**; `verify`, `backup`, `export` work alongside it. API-triggered purge waits for E6.
9. **`--confirm yes`** on `audit purge --all` as the scripted form of the typed word.
10. **The purge audit row is written in the same transaction as the delete**, and the head row in every append transaction.
11. **Overflow policy: drop newest**, separate caps for audit and raw rows, an `audit-overflow` row per batch that saw drops. Audit rows and raw rows have separate caps, so a chat flood sheds raw text without starving decision rows.
12. **Pseudo-id cache** (4 096 entries) so decision rows for a chat-triggered action carry the viewer's pseudo id even when the actor field does not.
13. **Worker is `unref`'d when idle** (ref'd while a message is pending), so a forgotten audit never keeps the process alive, but `flush`/`close` do wait.
14. **`createEventCore` closes the audit if the action gate cannot be built**, so the lock is not leaked.
15. **Tools:** `tools/audit-crash.mjs`, `tools/audit-crash-child.mjs`, `tools/bench/audit-writer-compare.mjs` (measurement, not a regression bench).

## UNVERIFIED and limits

- Power-loss durability of `synchronous=FULL` on this disk (only process kill tested).
- Tamper evidence is against edits that do not also rewrite the chain and the head record. Someone who can write the database file can rebuild both. Proposal (not built): anchor the head hash somewhere else on a schedule (a signed line in a file outside the data dir, or the OS event log), or HMAC the chain with a key kept apart from the data dir.
- Secure delete covers the SQLite files. Copies the operating system, file-system journal, SSD wear levelling, OneDrive or backup software made of the data dir before the purge are not covered. Do not put the data dir under a synced or backed-up folder (UNVERIFIED whether the user's `paths.event_core_data` will be).
- `incremental_vacuum` reclaims free pages at the end of the file; the test shows the file shrinks to 32 KiB in the synthetic case. A very fragmented long-lived database may retain free pages in the middle (zeroed by `secure_delete`, but not returned). The test proves no marker bytes; it does not prove the file never keeps zeroed pages.
- The data dir's file permissions: the database files inherit the folder's ACL. `pseudo.key` has its own ACL step (E1); the database does not. Raw chat is readable by any process running as the user.
- `node:sqlite` is used on Node 26.12.1 (SQLite 3.54.0). That it needs no flag from 22.13 is still UNVERIFIED (plan decision 7).
- Behaviour with the data dir on a network share (SQLite locks are unreliable there) is untested.
- Supervisor restart of a dead writer thread (P4/P5), E6 API purge, and the viewer-erasure design are open.
- PB-12 is not verified by this step (end-to-end ingest to dispatch is E7). The bench numbers above are the gate for "the audit adds almost nothing to ingest".
- Wall-clock `now` for `received_at` and retention is `Date.now()` at the time of the recorder call (or the injected clock); a machine clock set wrongly would purge too early or too late.
