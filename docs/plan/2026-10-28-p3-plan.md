# 2026-10-28 — P3 plan: Event Core, multi-chat ingest, moderation, live-lock, audit

Approved by the user on 2026-10-28. Build plan "Done when": real and mock chat flow; forbidden actions refused. The standing checks in `2026-10-28-core-build-order-and-checks.md` apply. Routing: Sonnet with medium effort; Opus reviews live-lock (E4); a fresh agent does the security review (E8).

## User decisions (2026-10-28)

1. **Chat route.** Twitch, YouTube and Kick all come in through Streamer.bot in P3.
2. **Native Twitch EventSub and Helix** are needed for channel-point fulfil/refund in chat scene control (C2), so they are planned in P12, not P3. The YouTube native API is optional and has no phase yet.
3. **Performance budgets** are approved and marked UNVERIFIED until measured. After the first benchmark run, each budget is replaced with the measured value plus a margin.
4. **Lint** is a stdlib script: `node --check`, `py_compile`, line endings per `.gitattributes`, SPDX licence headers, no trailing whitespace, no secret patterns (keys, tokens), no absolute user paths.
5. **Real chat test** is read-only, on a normal stream. In P3, replies go only to the mock. No message goes to any real platform until the user approves it in a later phase.
6. **Raw chat retention.**
   - Raw chat text is kept locally for 30 days, then only ids are kept.
   - The purge runs automatically on startup and daily. The user can also run it manually.
   - Raw chat never goes into backups, exports, evidence files, logs sent anywhere, or Jev calls.
   - After 30 days, the audit of a chat-triggered action keeps the action, rule, result, timestamp and a pseudonymous user id.
7. **Node version.** `engines` becomes `>=22.13`, the first version where `node:sqlite` needs no flag. This is UNVERIFIED; testing is on 26.12.1, which has SQLite 3.54.0.

## Blockers before C2/C3

Added 2026-10-28 by user decision. Existing text above is unchanged.

1. **Lost-action gap (idempotency residual window). BLOCKER.** A kill after the durable `started` commit and before
   `executor.execute` is called loses the action: a resend after restart is skipped as ambiguous, so it runs 0 times
   (never 2). See `docs/evidence/2026-10-28-p3-e7-stalls-idempotency.md` B2. P3 accepts this only because chat actions
   are dry-run in P3: every catalogue entry is `chatAllowed: false` and the service executor has no studio handlers.
   The gap must be closed, with a test that kills inside the window and shows the action runs exactly once (or is
   shown to the user and re-run on approval), before any chat-triggered action is switched on in C2/C3. Options are in
   B2 (the target takes the key; re-run of ambiguous keys for actions marked safe to repeat; dashboard re-run).
